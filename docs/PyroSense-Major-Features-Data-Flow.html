PyroSense System Documentation

How Data Moves, Generates, and Produces Outputs

A detailed implementation-based explanation of the system's three major features: fire-risk prediction, action-plan checklists, and mitigation management.

1. Prediction 2. Checklist 3. Mitigation Closed feedback loop
Prepared: 8 September 2026
Code snapshot reviewed: Git commit 0ec2a5c, including current workspace implementation
System stack: Laravel application, relational database, Python prediction runtime, OpenRouter narrative generation, and external weather services
Primary readers: capstone evaluators, BFP Chief/Station Admin, firefighters, barangay users, and developers
Purpose: explain where data comes from, how it is validated and transformed, what is saved, what users see, and how operational results become future prediction inputs.
Central interpretation rule: the prediction percentage is a barangay-month high-risk classification probability. It is not a guarantee that a fire will happen, and it is not the probability that a specific building will ignite.

1. Executive summary

PyroSense is designed as a decision-support cycle. The prediction module consolidates station-scoped incident records, historical barangay fire records, verified risk and hazard assessments, weather, environmental exposure, access and water conditions, and prior prevention work. A Python model produces barangay-level forecasts when available; a deterministic formula provides a safe fallback. The application then aggregates those barangay results into a station outlook and may use a language model to explain the result and propose operational recommendations.

Recommendations become stored action-plan checklists. Each checklist gives personnel a concrete sequence of tasks, owner, priority, deadline, expected result, and review state. Users review each checklist item as followed or not followed. A checklist can then be transformed into a mitigation draft. That draft is reviewed and edited by the Chief/Station Admin before it becomes an official mitigation action.

Mitigation actions carry assignment, schedule, progress, blockers, proof attachments, outcomes, effectiveness, verification, and follow-up. Firefighter or barangay completion is not immediately treated as final: it becomes a pending completion request, and the Chief/Station Admin approves or rejects it. Confirmed checklist and mitigation activity is summarized into readiness features for later prediction runs, completing the feedback loop.

3. Prediction: complete input-to-output flow

3.1 User request and scope

The Chief/Station Admin starts a prediction from Analytics. The request supplies a station/location scope, optional barangay, day window, current-month or next-month scope, historical window, and analysis kind. The authenticated user's station_officers record determines the station. A selected barangay must be within that station's active coverage.

  1. Normalize the requested scope and selected barangay.
  2. Resolve the Chief's station, station teams, and covered barangays.
  3. Read and aggregate source data only within that authorized scope.
  4. Build one model payload per selected/covered barangay.
  5. Run the Python model in a batch; if unavailable, use deterministic fallback values.
  6. Calibrate incident counts and aggregate barangay forecasts into the station result.
  7. Generate an explanatory prediction narrative and recommendations; fall back to application-generated text if the narrative service fails.
  8. Save the analysis, generated checklist records, checklist item rows, and recommendation suggestion records in one transaction.
  9. Return JSON to the frontend, which displays the analysis and later polls an asynchronous run when the API path is used.

3.3 Open-Meteo collection and forecast fields

For completed-day collection, the service resolves coordinates from active station–barangay coverage and barangay-hall markers. It calls Open-Meteo for a completed date in Asia/Manila, collects hourly temperature, relative humidity, precipitation, rain, weather code, wind speed and wind gust, summarizes them, and upserts one row per barangay/date/source. Retries are safe because the key is stable and existing rows are updated.

The visible forecast request uses current temperature/humidity/weather code/wind; daily weather code, maximum/minimum temperature, maximum precipitation probability, precipitation sum and maximum wind; and hourly temperature, humidity, precipitation probability and wind. Fresh results are cached for six hours and the last successful result may be retained for up to 72 hours. HTTP 429 is not immediately retried.

4. Prediction factor engineering

4.1 Historical fire baseline

For each barangay, the system distinguishes positive fire-incident history from rows that contain weather observations only. The incident baseline uses the larger available count:

historical_fire_baseline = max( sum of positive incident_count for the same calendar month in the historical window, sum of positive incident_count for the most recent 12 months )

This avoids counting imported monthly weather as if it were a fire. Historical risk context is labeled high at eight or more incidents, medium at four to seven, and low below four.

4.2 Recent fire momentum

recent_fire_momentum = 2.00 × fires_last_7_days + 0.65 × max(0, fires_last_30_days − fires_last_7_days) + 0.80 × fires_current_month − 0.35 × fires_previous_month

The signal emphasizes new acceleration. Station momentum is allocated across covered barangays instead of copying the full station total into every barangay.

4.3 Verified field-pressure signal

risk_area_pressure = 0.8 × verified risk-area count + 1.1 × verified hazard count + 2.5 × high assessments + 1.8 × blocked hydrants + 1.6 × combustible-material findings + 1.3 × informal-settlement findings + 1.2 × cooking-fire-prone findings + 0.8 × poor-waste findings + 1.6 × previous-fire-prone findings + 1.4 × difficult-access findings + min(affected households ÷ 25, 5)

Only approved/verified field evidence contributes to these localized signals. Descriptive values also become categorical model inputs.

4.4 Prevention/readiness feedback

Checklist priorities are weighted low=1, medium=2, high=3, and critical=4. The station analysis calculates confirmed checklist weight, item-followed ratio, mitigation completion ratio, blocked actions, and average completion days.

displayed readiness improvement = min(35, 18 × weighted checklist completion ratio + 12 × mitigation completion ratio + 5 × checklist item-followed ratio)
Important safeguard: this implementation does not automatically lower the hazard score merely because work was marked complete. risk_reduction_percent remains zero without measured and verified outcome evidence. Completion improves readiness reporting and future model features; it is not proof that the physical hazard disappeared.

4.5 Deterministic fallback probability

If the Python model cannot run, the analysis still produces an explainable fallback. The score starts at 12, rises with historical incidents, heat, low humidity, wind, verified risk pressure, and recent/station momentum, and falls with readiness and mitigation completion. It is clamped from 5 to 95.

fallback score = clamp(5, 95, 12 + 7 × historical incident count + 1.8 × max(temperature − 27, 0) + 0.35 × max(65 − humidity, 0) + 0.45 × wind + 2.4 × risk pressure + 2.2 × recent momentum + 0.55 × station momentum − 3 × mitigation readiness − 12 × mitigation completion ratio)

Fallback bands are Low below 35, Moderate from 35 to 64.99, and High at 65 or above. The row is explicitly marked deterministic_fallback, so it is not misrepresented as a trained-model result.

5.4 Evaluation caution

The metadata reports test accuracy 0.975, ROC AUC 0.9704, precision 1.0, recall 0.625, F1 0.7692, and Brier score 0.0219. The incident-count regression reports MAE 0.0151 and R² 0.4797. The damage regression reports R² −1134.9025, which is not reliable for decision-making. PyroSense now withholds the station damage output and excludes it from risk-band thresholds whenever the latest damage-regression R² is below 0.20. A later retraining run can restore the output automatically if the regression passes that threshold.

Operational conclusion: use probability, drivers, count range, evidence quality, and field validation together. Do not present the reported test metrics as guaranteed live accuracy. A weak damage estimate is displayed as unavailable instead of being treated as evidence.

6. Post-processing, station aggregation, and saved prediction outputs

6.1 Count calibration

The model count is calibrated using current observed pace and the same calendar month from up to three prior years. For current-month analysis, expected total is never allowed below observed-to-date fires. The saved/output structure separates observed fires, predicted additional fires, expected month total, and a planning range.

6.2 Station aggregation

Barangay predicted counts and damage estimates are summed. Station probability is a blend of the most urgent barangay and overall coverage:

station probability = 55% × highest barangay probability + 45% × average barangay probability

The station risk band is High if probability is at least 65%, predicted count at least 6, or estimated damage at least PHP 500,000. It is Moderate if probability is at least 35%, count at least 3, or damage at least PHP 150,000; otherwise Low.

6.3 Separate operational score

The recent station score uses incident rate (up to 30 points), fire rate (up to 30), fire share (up to 20), and a 20-point recent-spike condition, capped at 100. Bands are Low below 30, Medium 30–49, High 50–69, and Critical 70+. Current code keeps this base hazard score unchanged by mitigation completion.

6.4 Evidence-quality confidence

The maximum raw score is 65 points: historical years up to 15; scoped incidents up to 10; barangay forecast coverage up to 12; trained model availability 8; weather context 6; verified risk findings up to 6; current/previous fire trend 5; and successfully parsed prediction/recommendation narratives 3. The percentage is High at 75+, Medium at 45–74, and Low below 45.

6.5 Narrative AI versus numerical model

The application makes separate OpenRouter calls for the forecast explanation and operational recommendations. These calls explain and organize the supplied evidence. The Python/deterministic prediction values remain the grounded numerical source. If either narrative call fails, the application produces a data-driven analysis and records a warning; a narrative outage does not silently replace the numerical provenance.

7. Checklist: generation, movement, and output

7.1 Where checklist content comes from

After an analysis is saved, the application processes up to ten recommendations. If AI_GENERATE_ACTION_PLAN_CHECKLISTS=true, it may request structured checklist JSON. Otherwise—or when that response is missing or invalid—it creates deterministic recommendation-backed plans. A fallback plan uses the recommendation's title, description and steps; if steps are absent, it creates practical review, assignment, coordination and documentation tasks.

For station-wide analysis spanning multiple barangays, the system can localize the leading recommendation into one plan per barangay. This prevents a generic station plan from losing barangay ownership.

Updating items can automatically move a pending checklist to in progress and, when every item has been reviewed, to submitted. A user may explicitly confirm, reject, return to in progress, or submit when validation requirements are satisfied.

7.4 Validation and governance

  • Manual create/edit requires a plan title, description, success indicator, priority, valid status, target date and 1–50 checklist items.
  • Barangay, risk area and assignee must belong to the authorized station scope.
  • Every item must be reviewed before submitted/confirmed.
  • An item marked not followed must have a reason.
  • Submission/confirmation requires assignment and a target date.
  • If the linked analysis evidence score is below 45, confirmation requires a note explaining why approval is safe.
  • Editing a previously submitted, confirmed or rejected checklist resets review metadata and returns it to pending.
  • Regeneration reconciles by source signature. Operationally used records are protected and can be flagged for revision review instead of being overwritten.

7.5 Checklist outputs

The Chief/Station Admin sees status counts, priorities, overdue items, assignment, item progress, confirmation controls and history. Barangay and firefighter workflows can review assigned items. The Mitigation page can select checklist items and generate an editable mitigation draft. Later prediction runs receive aggregate checklist totals, confirmed weighted completion and followed-item ratios.

Terminology note: the checklist transformation is labeled “AI-Assisted,” but the current service performs a deterministic transformation of stored text and explicitly makes no additional AI request. The Chief/Station Admin must review and edit the result before saving.

8.2 System-generated mitigation suggestions

A manual refresh scans predicted risk areas in station coverage. A suggestion requires a primary risk area and barangay. Category is inferred from factors such as blocked hydrant, poor access, electrical/wiring condition, LPG/gas condition, combustible material, informal settlement or cooking activity. It includes local drivers, verified-record and historical-incident counts, support points, team/personnel/crew/hydrant/active-incident resource context, operational tasks, and a target date: seven days for high, fourteen for medium, and thirty otherwise.

Duplicate protection uses a stable signature combining risk area and category, locks the risk area during creation, preserves existing suggestions, and skips creation when an open action for that risk/category already exists.

8.6 Firefighter/barangay completion review

  2. Blocked requires a blocker. Completion requires completion notes, outcome, effectiveness and proof.
  3. A “completed” submission is stored as in_progress with completion_approval_status=pending; it does not close itself.
  4. The Chief/Station Admin verifies proof and outcome, then approves or rejects.
  5. Approval changes status to completed and stores decision/verification metadata. Rejection returns the action to in progress.

Every create, progress update, command edit, completion request, approval or rejection writes activity data and user activity logs.

9.1 Closed-loop sequence

  1. Observe: incidents, weather and verified field conditions enter the database.
  2. Predict: records are scoped, transformed into features and evaluated by the model or fallback.
  3. Explain: results expose probability, counts, drivers, provenance and evidence quality.
  4. Plan: recommendations become assigned, dated checklists.
  5. Act: selected tasks become reviewed mitigation actions.
  6. Prove: personnel record progress, blockers, attachments, outcome and effectiveness.
  7. Approve: station command accepts or returns completion.
  8. Learn operationally: summarized completion/readiness features enter later prediction payloads.
This is feedback, not automatic causality. The model can use completion history as a preparedness signal, but a completed record alone does not prove that a specific hazard was eliminated or that the next forecast must fall.

11. Illustrative end-to-end example

The values below are hypothetical and explain movement only; they are not a live forecast.

  1. Input: Barangay A has historical positive fire rows, two recent closed fires, a verified blocked hydrant, combustible materials, difficult road access, hot/dry weather, and one incomplete high-priority checklist.
  2. Feature construction: historical count, recent momentum, blocked-hydrant count, combustible count, poor-access count, weather features and incomplete readiness all enter the barangay payload. Weather-only historical rows contribute weather but zero fires.
  3. Prediction: the model returns a high-risk probability, predicted incident count, possible damage estimate and local drivers. If the model cannot run, the deterministic formula uses the same evidence groups and marks the result as fallback.
  4. Calibration: current observed fires and prior same-month counts constrain the expected total. The UI shows observed-to-date, additional expected fires and the month planning range separately.
  5. Recommendation: the narrative recommends restoring water access, clearing emergency routes and inspecting combustible storage, grounded in the supplied drivers.
  6. Checklist: a high-priority plan is stored for Barangay A with ordered tasks, owner, target date and success indicator. Personnel mark each item followed/not followed and explain exceptions.
  7. Mitigation draft: selected hydrant/access tasks are transformed into an editable Water Supply or Access & Routing plan. Nothing is saved until the Chief approves the form.
  8. Execution: the assigned team records inspection, repairs/coordination, implementation notes and proof photos/documents. If work is blocked, it records the reason.
  9. Completion: firefighter/barangay submission requests completion. Chief verifies proof and actual outcome, evaluates effectiveness, then approves or returns it.
  10. Next run: checklist confirmation, followed-item ratio, mitigation completion/open/blocked state and completion duration become readiness features. The underlying hazard score is not automatically reduced without measured evidence.

15. Glossary

AnalysisA saved prediction run with scope, evidence, outputs and revision.
Barangay-monthOne barangay evaluated for one calendar month; the unit of the trained classification target.
DriverA factor used to explain why a particular forecast rose or fell.
Evidence provenanceTrace information showing which historical, weather, incident and verified-field records supported the result.
FallbackA deterministic, marked calculation used when the trained model or narrative AI is unavailable.
MitigationA controlled preventive or preparedness action with owner, deadline, proof, outcome and review.
Readiness signalSummary of checklist/mitigation execution used as operational context and future model input.
Risk areaA verified/approved field record describing a localized risk or hazard and its conditions.
Source signatureA stable identifier used to reconcile generated plans and avoid duplicates/overwrites.

16. Final interpretation checklist for evaluators

  • Was the analysis station/barangay and time scope stated?
  • Were observed fires kept separate from forecast additions?
  • Was the prediction source identified as trained model or deterministic fallback?
  • Were probability, operational score and evidence quality treated as different measures?
  • Were local drivers and evidence freshness/provenance reviewed?
  • Was the recommendation converted into owned, dated, reviewable tasks?
  • Was mitigation saved only after human review?
  • Did completion include proof, outcome, effectiveness and command approval?
  • Was readiness feedback treated as context—not automatic proof of hazard reduction?
One-sentence system explanation: PyroSense turns authorized operational, historical, environmental and field evidence into a traceable barangay risk outlook, converts that outlook into assignable checklists, governs preventive work through evidence-based mitigation approval, and returns verified workflow results as readiness context for the next prediction cycle.
